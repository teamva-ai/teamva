# Issue 工作分配

## 用户入口

单个不同 Agent 的普通 `@` 保留直接发送，不调用整理模型、不增加确认步骤。同一 Agent 在正文中重复提及仍按同一身份去重，不自动解释成多份工作。

选择第二个不同 Agent 时，不再把它插成第二个普通激活目标；在当前回复框下展开工作分配并带入两个目标。手输、粘贴和发送快捷键使用同一检查，普通用户评论接口最多接受一个 `mentioned_agent_ids`。不会为了拦截而删除用户正文。

同一个 Agent 要并行执行多份工作，使用候选菜单的显式「分配多项」入口；工作表单允许重复选择同一 Agent。表单每项包含稳定 key、负责人、工作名称、可选详细要求和开始条件。开始条件只有立即执行或指定工作全部成功后执行，不提供流程画布、条件分支或隐式依赖推断。

进入工作分配后，本次评论只以 `work_items` 为激活依据，`mentioned_agent_ids` 必须为空；正文只作为共同背景，不再额外激活其中的 Agent。工作项 key 不是 Agent ID，也不随排序或改名变化。

## 编辑与提交

用户可以完全手动分配，不调用模型。可选的「帮我拆分」仅在显式点击后调用已明确选择的整理 Agent，并填入同一份可编辑工作清单；不会启动业务工作。

整理期间修改需求、选人、切换 Issue 或取消操作，会使旧响应失效。重新整理不得静默覆盖手动修改；失败保留已有草稿。最终发送使用当前确认的工作清单快照，不重新解析正文。提交失败保留草稿，迟到的成功不能清除提交后新编辑的内容或其他 Issue 的草稿。

`POST /v1/issues/{issue_id}/comments` 提交 `work_items` 时必须携带 `Idempotency-Key`；相同请求重试返回同一评论，不再创建工作。复用同一 key 修改工作定义返回冲突。评论、工作定义及可立即执行的 mentions 在同一 SQLite 事务提交。

编辑已发布评论的正文仅修正说明，不修改已确认的工作定义；任务表单不是通过改评论正文重新派活。

## 工作与执行实例

一份工作对应一个独立 mention 和新会话；同一 Agent 的不同工作可以并行，不隐含共享原生会话或文件隔离。实例内 Run 仍串行。

工作定义与关联保存在既有 `app_metadata`，不修改 SQLite 基线，不升级、回填或清理已有数据库。运行、原生会话、事件、审批与恢复仍复用既有执行链路，不增加第二套 Runtime。

`issue_work:v1:*` 保留完整历史；`issue_work_pending:v1:*` 仅索引尚未生成全部 mentions 的批次，随工作定义在同一事务维护。完成派发、取消或删除任务时撤销待调度索引，不删除历史。启动时只读校验两者一致性；索引缺失或损坏时保留原库并拒绝启动，不回填旧数据。调度 tick 只遍历待调度键，不反复解析已完成历史。

无前置的工作可立即调度；有前置的工作先持久等待，不调用模型轮询。只有全部指定工作成功，并通过现有工具发布了结果，才释放后续工作。Provider 结束不等于业务结果已发布；Goal 完成仍遵守既有审核与总结门禁。

前置失败、停止或缺少结果时，后续显示等待或阻塞，不自动视为完成。暂停、关闭、删除评论和清空队列的急停边界不能被工作调度绕过。后台调度与重启恢复必须幂等，重复通知不会重复启动后续工作。

本次不新增独立的全 Issue 暂停或清队列界面；沿用既有暂停会话、停止 Run 和关闭任务的边界。存储层清队列操作会同时取消尚无 mention 的等待项，避免后续完成事件重新唤醒；不能把这个存储能力说成已有新的用户按钮。

例如 A1、B1/B2、C1/C2/C3 六项可立即执行；A2 的 `after` 仅选 B1、B2、C1、C2、C3 时，它不等待 A1。若也要等 A1，必须显式加入。工作等待图不能形成环；这不禁止合法的 A1 → B1 → A2，也不改变既有允许 Agent 间接循环的语义。

`GET` 评论返回 `work_items` 状态投影，包括实例、Run、结果评论和阻塞依赖。用户刷新后仍能观察和打开对应会话。公开结果来自 Agent 的真实工具提交，不能把最终模型文本伪装成评论。

Agent 工具的结构化工作分配复用同一验证与事务边界，仍禁止直接分配给自己的 Agent ID；不能用新字段绕过 self-mention 或扩大只读助手作用域。

## 可选 AI 整理的安全边界

`POST /v1/issues/{issue_id}/work-plan` 接收整理 Agent、需求正文及明确允许的执行 Agent IDs，返回有界且严格校验的工作草案。HTTP 层从已保存 Agent 修订选择 Provider/模型，不接受任意模型、系统提示词或权限开关。

整理使用独立临时运行环境，并固定 `ReadOnly` 与严格 `DisableTools`，不加载项目目录、Skills、MCP、FileBridge 或 ToolBroker，不创建业务 Run、评论、mention 或实例。取消必须等待 Provider 关闭后再清理私有目录。

Provider 必须显式声明 `no_tools` 且真实实现该边界；不支持时在模型调用前拒绝，不能以 readonly、空工具展示或提示词约束降级，也不能偷偷更换 Provider。不支持整理的 Agent 仍可作为用户确认后的工作执行者。

模型输出只允许明确的字段、目标白名单、有效工作 key 和无环依赖；未知/重复字段、尾随 JSON、越权 Agent、超限输出或失败终态均拒绝。原始模型正文、Provider 错误和认证数据不进入错误响应或日志。自然语言理解仍可能有误，草案必须经用户确认才能提交工作。

## 验证范围

- 单 Agent 发送、重复同 Agent 提及及原有 Markdown/重名身份解析回归。
- 第二 Agent 候选点击、键盘选择、参与者按钮、手输/粘贴及直接发送不能绕过。
- 同 Agent 多项、当前清单编辑、依赖选择、环检测、草稿恢复和迟到响应隔离。
- 多工作原子提交、并发幂等、跨用户/项目目标拒绝、失败和结果缺失阻塞、急停与重启恢复。
- 整理调用的严格 NoTools、输出校验、取消清理与确认前零业务激活。
- 真实浏览器覆盖桌面与触摸窄屏；真实模型、Wails 和发布制品另行提供证据，不能用自动化替代。
