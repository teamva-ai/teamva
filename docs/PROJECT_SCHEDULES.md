# 项目定时任务

项目左侧的「定时任务」（`/schedules`）集中管理当前项目的自动执行请求，不另建一套与原计划任务并行的调度器。新建时填写名称、提示词、已配置的普通 Agent、Issue 目标和时间规则。

## Issue 目标

- **每次新建 Issue**：每次触发在该项目内新建 Issue，以本次提示词激活所选 Agent，执行记录可追溯到 Issue 与 Run。
- **使用已有 Issue**：仅选择当前项目的可用 Issue。触发时向该 Issue 追加执行请求，保留公共协作上下文；不会自动重开已关闭的 Issue，不绕过暂停或恢复已停止的 Agent 实例。
- 选择器只提供当前项目电脑上已启用、有配置修订的 Agent；配置后的 Lumi 与普通 Agent 一样可作为业务定时任务 Agent，不再按 `system_role` 排除。
- 时间到达不是直接绕开队列调用模型。请求必须经过既有 Issue/mention/Run 持久化与调度，Agent 完成后仍须通过 `issue_comment_create` 发布公共总结。

## 时间配置

| 类型 | 配置 |
| --- | --- |
| 每天 | 一个或多个精确 `HH:mm` 时间点 |
| 每周 | 选择星期（API 为周日 0 至周六 6）和多个时间点 |
| 单次 | 在所选 IANA 时区输入日期与时间，保存 RFC3339 绝对时刻 |
| Cron | 五字段表达式及常用预设 |

每天与每周的时间是完整时分对。例如 `09:15` 与 `17:45` 不会错误展开成四个触发点。时间列表去重、排序，最多 64 个；每周至少选择一天。预览由服务端计算，按所选时区显示，前端不以自己的 Cron 推导代替实际执行算法。

单次日期不依赖浏览器本地时区偷换所选时区：夏令时缺失的墙钟时间无效，重叠时选择较早的绝对时刻，保留秒与毫秒。编辑其他字段不会截断原有时间精度。

应用关闭期间不会执行定时任务。新任务默认禁止自身重叠运行、跳过错过的触发；保留既有并发和错过策略时，以保存的策略为准。

## 接口与 UI 边界

- 项目 CRUD 沿用 `/projects/{id}/scheduled-tasks`、`/scheduled-tasks/{id}`，预览沿用 `/scheduled-tasks/preview`，不分叉第二套 HTTP 调度服务。
- 每日/每周使用 `schedule_kind`、`times`、`weekdays`、`timezone`；单次/Cron 使用 `schedule_expression`。Issue 目标使用 `issue_mode` 与 `issue_id`。
- `SchedulePicker` 在 `web/src/ui` 中复用 Input、Select、DatePicker、Checkbox、Button 和 Field。配置及时间转换工具位于 `web/src/lib/scheduleConfig.ts`。
- 新建与编辑共用分列弹窗：视口宽度至少 960px 时左侧为名称、Issue 目标、Agent、时间/时区与预览，右侧仅为提示词；更窄时按配置、提示词顺序上下排列。提示词复用 Field/Textarea，长内容在文本框内部滚动；弹窗仍沿用共享 Modal 的自然高度、正文滚动与固定页脚，不引入左右独立滚动或 sticky 面板。
- 保存请求捕获项目、目标任务与表单版本，不因切换项目误写到新项目，也不在旧请求完成后关闭另一个新表单。
- Issue 列表加载失败不是空列表；提供重试并禁止误保存。已删除、关闭或不可访问的原目标明确显示不可用，不静默改成新建 Issue。
- 运行记录保留每次触发的幂等键、时间、状态及 Issue/Run 入口；同一触发重放不得多建 Issue、评论或 Run。

## 持久化与恢复

不修改 SQLite 基线或迁移现有库。扩展时间与 Issue 目标放在既有 `app_metadata` 的 `scheduled_task_config:<id>` 强类型记录中，与任务主记录共用事务、版本锁与恢复边界；统一读取通过 LEFT JOIN 水合，不在列表中逐条额外查询。

有扩展配置的任务在主记录使用保留的非法日历标记，防止 metadata 丢失后被误当成普通独立任务执行。配置缺失、损坏或不合法时拒绝执行，不静默回退、自动清理或创建新目标。即使是没有扩展配置的历史单次任务，手动与自动触发也校验日历/时区；合法的已到期时间不会被当成损坏配置。

没有扩展记录的历史单次/Cron 任务保留原独立运行语义与历史，暂停/恢复不会改变它们。通过新编辑器明确保存为 Issue 模式后才切换；新建 HTTP 请求默认每次新建 Issue。创建新 Issue、真实用户提示评论、mention、Agent 实例、Run 与触发记录在同一事务提交，不产生“只建了 Issue 没有执行记录”的半完成状态。

已有目标结束、删除或存在暂停会话时不绕开急停。自动派发发现永久性目标错误会隔离该任务，并保留可见错误；同一次触发重放不创建第二套业务记录，并发禁止也在创建 Issue 之前检查。

## 验收边界

Domain/SQLite/API 测试覆盖实际触发与事务语义；真实 Chrome 用例只保存未来计划，并将「立即运行」作为请求契约 fixture，不消费真实模型额度。真实 Provider 的执行与公共总结仍须在用户授权账号、隔离资源上另行验收。

`scripts/e2e/schedules.spec.mjs` 的分列几何回归在 1280/1024px 验证左右分列、800/390px 验证上下堆叠，使用真实 border box 覆盖新建/编辑、新建/已有 Issue、每日多时间/每周/单次/Cron、长提示词内部滚动、横向边界和固定页脚可操作性；不以 CSS 类或单纯无溢出代替几何断言。分列用例只持久化 2040 年的单次任务，其余调度类型仅切换草稿，编辑后取消，并拦截意外的 run-now 请求；既有每日/每周保存用例使用距当前 UTC 时间约 12/13 小时后的时间点，避免 QA 期间自动触发。字段配对对齐仍由 `field-layout.spec.mjs` 独立验证。
